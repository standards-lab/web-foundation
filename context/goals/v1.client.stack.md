## Task brief · v1.client.stack · template

```
Problem       A web client on the stack has no starting point: a project
              is copied together by hand from the spike, and nothing
              writes one, installs it, or proves that what it writes
              builds and passes its own check. The architect set a CLI
              as the way in, with one leaf per kind of app; this task
              ships the CLI with the standalone kind and leaves the two
              embedded kinds to the next task.
Behaviors     1. `webappgen new standalone <dir>` writes a standalone
                 project into dir: the shared starter app, then the
                 standalone kind's own files, with --name (default: the
                 directory's name), --title (default: the name), --base
                 (default "/") and --api-base (default "/api/") filled
                 in. It never prompts. A dir that exists and isn't empty,
                 a missing dir argument, an unknown flag, or a --base
                 that doesn't begin with "/", isn't clean, or carries a
                 query or fragment is a usage error naming the fix, and
                 nothing is written. On success it prints the next
                 steps (mise install, mise run install, mise run check)
                 and exits 0.
              2. With --install, it then runs mise install and mise run
                 install in the written project. A missing mise or a
                 failing step exits nonzero naming the step; the written
                 files stay.
              3. `webappgen version` prints the release the binary was
                 built from, or (devel) when it carries none. Help
                 covers every command, `new` lists its kind leaves, and
                 exit codes are go-core's.
              4. The written project is private and takes
                 web-foundation v0.3.0, web-components v0.1.0,
                 web-app-sdk v0.1.0 and web-tooling v0.1.0 by exact
                 github: release tag, with a committed lockfile. Its
                 tools pin chrome-headless-shell for linux-x64,
                 linux-arm64, mac-x64 and mac-arm64. Its mise config
                 carries one comment naming the webappgen version that
                 wrote it, and no webappgen pin.

                 and Vite's base agrees with it. A render-blocking
                 module applies the reader's stored theme before first
                 paint, under the web-foundation.* storage keys, and
                 defines the theme menu. The page shows one
                 web-components element. web-app-sdk's router serves a
                 home view and a not-found view under the base, and a
                 deep link or a reload on a host that answers the page

              6. The app's config reader takes #app-config when the page
                 has one, and otherwise fetches config.json relative to
                 the base. A missing, non-JSON, or wrong-shaped config

                 server, preview, and build all carry.

              8. currency exits 0, both the CLI's and a written
                 project's, except for the recorded holds: typescript
                 at 6.0.3 (typescript-eslint's range), and rolldown at
                 the newest release in Vite's dependency range.
              9. The embedded trees hold only files git tracks: no
                 node_modules, no dist contents. The starter's tool pins
                 equal the CLI's own root pins.
              10. A vX.Y.Z tag on main's merge commit releases the CLI.
                  The release refuses a tag whose commit isn't on main,
                  runs the check, and builds linux and darwin on amd64
                  and arm64 with cgo off. It refuses any binary whose
                  `version` isn't the tag, and attaches
                  webappgen-vX.Y.Z-<os>-<arch>.tar.gz (binary and
                  LICENSE) and SHA256SUMS to a draft made from the tag's
                  CHANGELOG section, publishing only once every asset is
                  attached.
              11. README covers installing (mise use
                  github:standards-lab/webappgen, go install ...@latest),
                  WSL on Windows, `new standalone` with its flags and
                  --install, deploying a standalone build (replace the
                  built config.json; the host answers the page for
                  unknown paths), and the capability map. STANDARDS
                  holds the spike's judgement calls that apply, with
                  architecture pointers. Every file copied from
                  spike-html-apps (2883d78) carries a provenance line,
                  starter files included, so written projects inherit
                  them; JSON files' provenance lives in context.
                  CHANGELOG 0.1.0 names that source.
Test seams    The webappgen binary, run one shot at a time through
              go-core's processtest in the integration tier: its output,
              its exit codes, and the tree it writes. The full-proof
              case writes with --install and --base /app/ into a

              warms, then runs the written project's own check there.
Slices        No upgrade slice: the repository has no prior pins.

                 Demo: the check; `webappgen version`; usage errors.
              2. The project written: the shared starter and the
```

## Decisions

- plan: each repository starts fresh at v0.1.0, seeded by copy from its archived spike with a
  provenance line on every copied file; never a repository transfer, and the spike is never a
  dependency.
- plan: root is web-foundation, the layer every other builds on and the repository of two tasks;
  rejected web-tooling (first task only) and web-app-sdk-template (last task only).
- plan: `order` places the five as their own chain, web-tooling → web-foundation →
  [web-components, web-app-sdk] → web-app-sdk-template, between the templates' layer and
  go-web-service; rejected spreading them into the Go layers. They stay outside `exclusive`.
- plan: per-task locks: `newclient` adds go-web-sdk (and so the exclusive group) to the goal's
  repos for that task only, dropping it at its SHIP; `standard` adds architecture for that task
  only.
- plan: the catalog declares no `standard = "web-elemental"` until `standard` founds it; until
  then each entry cites the preliminary standard, web-client.md "Toward Web Elemental".
- plan: web-tooling v0.1.0 includes the pinned DejaVu font-set helper from spike-html-go-wasm;
  web-foundation doesn't adopt it.
- plan: Firefox's missing `blocking="render"` is accepted (a one-frame theme flash for readers
  with a non-default stored theme); no inline head script. Revisit when Firefox ships it.
- plan: Safari's missing CSS module scripts mean a page using the components or the theme menu
  requires a Vite build; the packages keep the standard syntax, no pack-time rewrite. Revisit
  when Safari ships it.
- plan: `palettes` refines the color profiles from https://terminalcolors.com/; the site states
  no license, so each palette's upstream license is checked before use.
- plan: tooling → foundation stay lean: sites.status-reports and sites.training.foundation are
  staged by a `plan` once web-foundation v0.1.0 is tagged.
- plan: init commits carry only the marathon setup; each repository's first task seeds its code,
  toolchain, CI, and release workflow.
- tooling: `release.yml` runs on the hand-pushed annotated `vX.Y.Z` tag instead of cutting the tag
  on a push to main, as the spike did. It verifies the tag (one parent, a merge commit on main,
  whose `package.json` version the tag names), runs the check, diffs the pack against the tag's
  tree, and publishes.
- tooling: the DejaVu font directory comes from `DEJAVU_FONTS`, as `BROWSER_EXECUTABLE` names the
  browser; the package ships no fonts.
- tooling: currency reads DejaVu's latest from its release asset names sorted by version, since
  mise's http backend lists them unsorted.
- tooling: the screenshots tests' stub PATH holds only the stub directory and a node symlink, so a
  node in /usr/bin can't let the real kitty or xdg-open bypass the stubs.
- tooling: held typescript at 6.0.3: 7.0.2 is outside typescript-eslint 8.73.0's range
  (`>=4.8.4 <6.1.0`); currency compares typescript against that range's newest.
- tooling: the JSON files' provenance (`package.json`, `.prettierrc.json`) lives in web-tooling's
  `context/README.md`, since JSON takes no comment.
- tooling: release.yml runs on `workflow_dispatch` with the tag, from main: a tag push reads workflows
  from the tagged tree, which holds only the pack, so the push trigger never fired (fixed forward in
  web-tooling #2); v0.1.0 kept its first cut, whose parent is main's merge commit, and released.

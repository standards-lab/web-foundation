## Task brief · embedded

**Problem**

webappgen v0.1.0 writes only a standalone client; nothing writes a client embedded in a Go
service and served by go-web-sdk v0.18.0's NewClient, which v1.client.reference needs. v0.2.0 adds
the kind, `service-app`, for new and existing services.

**Behaviors**

1. `webappgen new service-app <module> <dir>` copies go-web-sdk-template at its pinned tag as
   `<module>` into `<dir>`, by running gonew at its pinned x/tools version through `go run`. It then
   installs the app into the copy as `inject` does. Before anything is written, each of these is a
   usage error that names the fix:
   - a missing or extra argument;
   - a module path Go refuses;
   - a directory that exists and isn't empty.
2. `webappgen inject service-app <service-dir>` installs the app into an existing service. Before
   writing anything, it refuses a directory with no Go module, and one whose client directory
   already exists. `inject` is a top-level group with this one leaf.
3. Both leaves take `--name`, `--title`, `--base` (default `/`, standalone's base rules),
   `--api-base` (default `/api/`), `--client-dir` (default `client`), and `--install`.
4. The client is the starter with the service-app files laid over it.
   - It has no `index.html`, public directory, dev server, dev page, proxy, or `preview`.
   - Its Vite build takes the entry, theme, and page modules as inputs, at base `./`, with a
     manifest, into its own gitignored `dist/`.
   - Its Go package exports only `Dist`, `Entry`, and `RenderBlocking`. `RenderBlocking` lists the
     theme module, then the page module.
5. The page module draws the application page's header, Help and Settings dialogs, and glyphs into
   NewClient's empty body before first paint. A unit test holds its markup equal to standalone's
   page body.
6. The client's browser tier serves the build behind a shell rendered from its manifest, the way
   NewClient renders it, with `#app-config` inline. It passes the starter's page, dialog, glyph,
   theme, and routing cases.
7. The wiring adds a client file to the service's composition root.
   - The file defines `Dist` and `Client` nodes. NewClient gets the base, the title, the entry, the
     `RenderBlocking` list, and the config `{"apiBase": <--api-base>}`.
   - At base `/`, the client mounts through `Router.SetNotFound`, so the API, the admin mount, and
     the probes answer first. Under a prefix, it mounts through `NewHandlerModule` at the base
     without its trailing slash.
   - The wiring inserts at three anchors by byte offset, then formats with the standard library.
     Every existing comment stays in place. The anchors are the `Nodes` struct, the `defineServer`
     call in `New`, and `newRouter`'s return.
8. The Go wiring is all or nothing. If any anchor is missing, the kind still writes the client and
   the client file, but edits no existing Go file. It prints each remaining edit and exits nonzero.
9. The service's `mise.toml` gains:
   - a client build that `check`, `test`, `integration`, and `serve` depend on;
   - the client's own check inside the service's `check`;
   - a `dev` task that runs `vite build --watch` in the client beside air, herald-style;
   - the air pin, `aqua:air-verse/air` 1.67.4.

   A new `.air.toml` rebuilds the server on Go, JS, and CSS changes. It excludes the client's
   source, tests, scripts, and `node_modules`, as well as `tmp` and `bin`, and it sends an
   interrupt.
10. The service's CI workflow installs and builds the client before both of its jobs. The check job
    also installs the client's tools.
11. The `mise.toml` edit and the CI edit are each made only when the file matches
    go-web-sdk-template's; otherwise the kind prints the edit. `inject` never overwrites an
    existing `.air.toml`; it prints the edit instead.
12. `--install`:
    - Under `new`, it runs `mise install` and `go mod download` at the service root, then
      `mise install` and `mise run install` in the client.
    - Under `inject`, it runs only the client's two steps.

    Each step is named on stderr. A failing step exits nonzero and names that step and the steps
    left.
13. The printed next steps are the steps `--install` would run, then `mise run check`. Under `new`,
    `git init` comes first. There is no `mise trust` step.
14. The starter's README template renders standalone's README byte-identical, and a unit test
    holds it. For the service app it gives:
    - Tasks: no client `dev` or `preview`; the service's `dev` and `serve`.
    - Config: `#app-config` from the wiring's constant.
    - Deploy: build the client, then the service.
    - The page: as the page module draws it.

    The service's own README is left unedited.
15. `mise run currency` reports the template pin and the gonew pin when either trails. It reads
    them from their constants by a fixed pattern, which a unit test holds.
    - `mise run install` warms the module cache with both pins and the template's requirements.
    - webappgen's root `mise.toml` pins air, which the tools-equality test holds.
16. The integration tier proves both leaves offline, from the warmed module cache and pnpm store.
    - It writes the app with `--install`.
    - It runs the client's check, builds the client, and runs the service's vet and tests.
    - It starts the service and fetches the shell, an asset, and a deep link, both at `/` and under
      a prefix.
    - It proves `inject` on a freshly generated service, and on a service whose root differs.

**Test seams**

- The built CLI through the integration harness's `Run(t, args...)`.
- The wiring, one function over a service directory returning the edits applied or left, on
  template-shaped and differing fixtures; the matches-or-print edits, on fixtures.
- The rendered starter templates; the written project's check; the running service over HTTP;
  `currency.sh`'s pattern.

**Slices**

1. `new service-app` generation: the leaf, its arguments and usage errors, gonew at the two pinned
   constants, the currency lines, pattern test, and warming; an integration case generates a
   service offline and runs its tests.
2. The service-app client: the starter with the kind's files over it, the Vite build into the Go
   package, the page module and its markup test, the manifest-rendered shell, the README's kind
   conditionals (standalone byte-identical); an integration case runs the client's check.
3. The Go wiring on a template service: the client file, the three anchored edits, and `--base` at
   the root and under a prefix. An integration case builds, vets, tests, and starts the service,
   then fetches the shell, an asset, and a deep link.
4. `inject service-app`:
   - the top-level `inject` group and its leaf, sharing the client and the wiring;
   - all-or-nothing, with printed edits;
   - proven on a generated service and on a fixture whose root differs.
5. The service's toolchain:
   - the `mise.toml` edit: client build dependency, client check, `dev`, and the air pin;
   - `.air.toml`;
   - the CI edit, matches-or-print;
   - air in webappgen's root `mise.toml` and the equality test;
   - an integration case that runs the service's tests through its tasks.
6. `--install` for both leaves, the next steps, the README's service-app sections, the capability
   map in `context/README.md`, and the CHANGELOG's v0.2.0 section.

**Out of scope**

Editing go-web-sdk-template, go-web-service, go-web-sdk, or the exclusive group; a dev server for
the client; editing a service's README or `.gitignore`; a `dist/` placeholder; running `git init`
or air in a check; Windows.

**Door**

One-way for the `v0.2.0` tag, which reaches users; two-way before it.

**Release**

`v0.2.0` (webappgen).
